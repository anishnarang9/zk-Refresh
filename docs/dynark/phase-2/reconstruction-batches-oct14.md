# Bounded reconstruction batches: design and implementation plan

> For the assigned Sol worker: use the existing subagent-driven-development workflow. ROOT owns architecture, review, documentation and execution. Worker-authored code, tests and launchers require source review before the single heavyweight queue executes them.

**Goal:** reduce group-arithmetic latency during pending dynamic updates while preserving exact serial results, transaction rollback and the existing resource limits.

**Architecture:** immutable reads feed a bounded parallel arithmetic batch; one serial owner journals and publishes its results in the original action order. The initial candidate affects only `advance_update`, with no public configuration or persistence-format change. Rust, arkworks BN254 and the already pinned Rayon dependency remain unchanged.

## Evidence and decision

The preserved credential run and source review identify serial group arithmetic as a reconstruction bottleneck: the current algorithm requests 52,428,800 group scalar calls at domain size 1,048,576. The arithmetic-only source002/runtime002 pilot passed all 90 pair comparisons and 120 independently derived output checks across 15 cases. It exercised 8,192-operation batches at forward stages 1, 10 and 20, inverse stage 20 and inverse-domain scaling, with dense, one-in-eight and zero points. The final inventory was 1,491,064 requested scalar calls below the fixed 1.5-million ceiling. Pilot observations justify an integration candidate; they do not establish production reconstruction throughput or reduced total CPU work.

Three approaches were considered. Retaining serial arithmetic preserves the existing implementation but leaves the measured bottleneck. Parallel mutation of the pool would complicate journal ownership, publication and cancellation. The selected approach computes an owned, ordered result buffer from immutable pool references, joins workers, then publishes serially. Its extra bounded buffer must fit the existing private/global structural limits.

The initial production candidate uses **exactly 8,192 operations per parallel batch**. Smaller budgets or stage tails remain serial. Eligible work is a group stream in Forward/Inverse with stage greater than zero, or a group stream in Scale. A batch stays within a single phase, stage and stream. Materialize, Prepare, bit reversal, field streams, Pointwise, Integrate, headers and promotion remain serial. Generalizing thresholds or phases is a separate measured decision.

## Frozen contracts

1. `advance_update_with`, `advance` and `advance_with` retain their current serial behavior and observer ordering. `advance_update(0)` remains a no-op. The non-callback path may share a private implementation with an explicit batching policy, but must not introduce an exported behavior flag.
2. Before batch arithmetic, validate the pool, roles, cursor and all ranges. The batch length must fit the caller's remaining action budget, the pending transaction quota and the eligible stream/stage tail. No batch may cross promotion or depend on an output from another operation in that batch. Derive physical indices and roots exactly as the existing serial step does.
3. Worker closures receive immutable inputs and disjoint output slots only. No pool, journal, cursor, transaction or ledger mutation occurs in a worker. Join every worker before any publication or rollback. No unsafe code, detached work or new panic-catching contract.
4. Allocate at most one batch result vector with fallible reservation. Include all vector capacity and any index/root buffers in scratch accounting. Check the requested structural peak before reservation and actual capacity afterward, before arithmetic. The peak includes the existing pool, retained journal, old and pending roots with shared maps deduplicated, pending statement capacity and shared public material. Avoid whole-domain scans or clones. Insufficient scratch room or reservation failure selects the original serial path without changing proof/state semantics; inconsistent base accounting remains an error. Drop the buffer before returning.
5. Publish results in increasing original action order. Journal all physical preimages for an action before its first store, including both butterfly cells. Update progress and cursor exactly as a successful serial action would. The cursor describes the published prefix; scratch results never become persisted progress. Preexisting journal records from earlier calls remain available until the entire pending update commits or rolls back.
6. Account performed speculative arithmetic even if a later publication fails. Charge each batched requested scalar call and attempted action once, separately from cursor deltas. Do not double-count during serial publication. Committed counters advance only when the whole pending update commits, and no discarded work is counted as committed. Preserve saturation behavior. These are requested-call counters, not hardware instruction or CPU-time counters.
7. Any supported typed failure after computation joins all workers and rolls back the entire pending transaction, including earlier successful progress calls, through the existing journal. Cancellation between calls uses `cancel_update` unchanged. Test-only fault injection may exercise publication failures through a private seam; it must not change public callback behavior.
8. Keep the authenticated checkpoint format and existing pending-state policy unchanged. `dynamic/persistence_codec.rs::encode` rejects a pending update or dirty journal with `Error::Busy`; preserve and test that rule. Recovery checks cover a committed state with partial reconstruction and a state after cancellation. Recycled physical slots after promotion must retain correct preimages.
