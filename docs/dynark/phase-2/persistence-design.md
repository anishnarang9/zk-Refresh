# Persistence transaction requirements

October 10, 2026. Parent architecture record preceding T6 implementation. The concrete state schema, bounded encoding, AEAD dependency and runtime evidence are not yet implemented or approved. This document fixes the crash/rollback boundary already required by `architecture.md`.

The trusted provider is external to the attacker-replaceable cache directory. It supplies a protected encryption key and the expected committed identity for one package/holder/action session. A synthetic provider is sufficient for local tests. An in-memory provider only promises process-lifetime rollback protection; restoring the entire local directory and an equally rollbackable provider cannot provide persistent rollback rejection. OS key-store and remote authority integrations remain later work.

Use immutable, uniquely identified encrypted commit files rather than overwriting the only old generation before trust advances. Required ordering:

1. Validate the complete candidate state and checked encoded-size bound. Obtain fresh nonce material through fallible caller cryptographic randomness. The authenticated header binds version, package/setup/reduction/domain, holder/action, generation, commit identity and exact payload length. Private witnesses, projections, blinders and reconstruction state remain encrypted.
2. Write a new private temporary file using exclusive creation; finish authenticated encryption and all writes, then synchronize the file. Close it before publication. Do not interpret any unverified partial plaintext as state.
3. Publish that unique commit file atomically, then synchronize its parent directory. Retain the previous trusted file. The new file is still an uncommitted orphan until the trusted provider advances.
4. Compare-and-set the trusted expected commit from the exact previous identity to the new identity. A failed compare-and-set does not commit the new generation. Never substitute the maximum filename, newest timestamp or largest unauthenticated generation for this check.
5. Only after the trusted commit succeeds may obsolete files be retired. Cleanup failure is reported separately and cannot roll the trusted state backward.

On recovery, consult the trusted identity and open only its exact committed file. Before large allocation or group arithmetic, reject unknown formats, oversized declared/file lengths, incompatible public identity and invalid generations. Authenticate ciphertext before constructing sensitive engine objects. Decode with bounded counts and canonical field/group checks, recheck the complete state invariants, and require exact committed identity. If any required trusted material or committed file is missing, return explicit rebuild; do not guess an older usable state. Orphans do not authorize proofs.

Interruption tests must cover each write/publish/sync/trusted-commit boundary, corruption and truncation at boundaries, replacement with an older valid authenticated file, header/ciphertext cross-session swaps, nonce-source failure, and concurrent stale compare-and-set. Before trusted commit, the old complete generation must remain recoverable; after it, the new durable generation must be recoverable or a storage failure must produce explicit rebuild. Filesystem tests establish behavior on the test host, not universal storage durability.

The live-memory budget includes the engine's active/rebuilding states, transaction scratch, plaintext/ciphertext buffers, decoding allocations and public package. Prefer a bounded in-place AEAD buffer where supported; no streaming-authentication claim may expose unauthenticated state. Public artifacts remain separately shared. Full schema round-trip must preserve a partially progressed builder, its frozen snapshot/cursors, exactly-once pending corrections, active generation and current proof; alternatively an explicitly chosen rebuild record must not be labeled a resumed builder.

Own revocation, issuer disablement and action completion invalidate use through explicit trusted-provider hooks and erase/retire the local session's access to private state as supported. No claim of physical secure erasure follows from unlinking or Rust drop. Fresh issuer status and execution-current-root checks remain external application obligations; neither authenticated persistence nor local generation advancement supplies them.
