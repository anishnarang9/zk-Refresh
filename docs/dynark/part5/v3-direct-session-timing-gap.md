# Direct complete-session timing gap

**Scope:** read-only comparison of the economic gate with the current Training-011 and heldout timing/accounting code. This note makes no measurement claim and proposes no implemented change.

## Requirement from the application-benefit plan

The economic gate asks for a matched, directly timed complete-session Full/Anchor comparison at a justified update pattern, with all extra DYNARK work charged, a 20% target and observed spread disclosed, and a measured break-even distribution. It specifically says not to turn warm stage latency, a synthetic root sequence, or separate run medians into a session win ([plan lines 19–22](../../superpowers/plans/2026-10-16-v3-x509-application-benefit.md#L19), [87–90](../../superpowers/plans/2026-10-16-v3-x509-application-benefit.md#L87)). Its workload inventory includes credential preparation, witness generation and import, relation validation, delta construction, proving or refresh, ordinary verification, local state catch-up, serialization/reload, application submission/effect, failures/retries, wall time, CPU, memory/storage, and transaction costs ([plan lines 87–89](../../superpowers/plans/2026-10-16-v3-x509-application-benefit.md#L87)).

The key distinction is between a duration captured by a monotonic clock around one operation and a total made by adding durations captured around separate operations. A component sum can be useful cost accounting, but it is not a continuous measurement of the complete lifecycle.

## Training-011 timing map

The total summarizer computes paired deltas, savings fractions, medians, spread, and sampled crossings from those sums ([summarize_v3_campaign_total.py lines 205–223, 243–255, 300–323](../../../tools/part5/summarize_v3_campaign_total.py#L205)). | One-time setup and cohort issuance | Development setup uses `elapsed_ms`; cohort preparation uses start/end Unix-nanosecond fields ([reconcile_v3_campaign_costs.py lines 203–220](../../../tools/part5/reconcile_v3_campaign_costs.py#L203)). | These costs are reported separately and are not silently charged per request. They are not part of the pair totals. |

Thus, Training-011 has a direct wall measurement for the bounded session command, and direct component measurements for clone and common state work. Its reported Full/Anchor component totals are sums of those observations, not a single timer spanning the charged lifecycle. The outer command does include finalized application effect execution and cleanup; application transaction bytes, compute units, and fees are separate confirmed transaction metrics, not extra wall durations ([analyze_v3_campaign_economics.py lines 800–809](../../../tools/part5/analyze_v3_campaign_economics.py#L800)).

The training result does not qualify complete-tree CPU: the analyzer reports zero qualified sessions and describes the available CPU readings as overlapping wait4 attribution and sampled-tree lower bounds ([analyze_v3_campaign_economics.py lines 793–799](../../../tools/part5/analyze_v3_campaign_economics.py#L793)). RSS and storage are sampled outer-process peaks, not retained-memory lifecycle measurements. The current session path has no explicit serialization/reload stage or retained-byte accounting in its registered stage list ([run_v3_campaign_session.py lines 355–471](../../../tools/part5/run_v3_campaign_session.py#L355)). Failed or retried session attempts are not represented as successful matched-pair time: the matrix requires a passing uncensored slot, and reconciliation requires all current slot reports to validate ([run_v3_campaign_matrix.py lines 454–517](../../../tools/part5/run_v3_campaign_matrix.py#L454), [reconcile_v3_campaign_costs.py lines 128–170](../../../tools/part5/reconcile_v3_campaign_costs.py#L128)).

## Heldout timing map

The heldout runner has stronger per-step journaling, but it still does not directly time one continuous Full or Anchor lifecycle. `Journal.run_step` takes monotonic start/end readings around each job, retains a helper-reported duration when larger on an uninterrupted job, and adds measured failed attempts when resuming ([run_v3_heldout_case.py lines 696–763](../../../tools/part5/run_v3_heldout_case.py#L696)). Individual proof jobs include the complete refresh and have their own bounded subreports ([same file, lines 2094–2108](../../../tools/part5/run_v3_heldout_case.py#L2094)); effect/execute jobs also have bounded monitor reports.

The `pair-view` credential-preparation job is also directly timed as its own journal step; the analyzer can report that value separately and add it once to each B mode in its `plus_pair_view` view ([analyze_v3_heldout_costs.py lines 131–154, 1033–1044, 1069–1082](../../../tools/part5/analyze_v3_heldout_costs.py#L131)). The runner then builds branch component sums: Full A uses proof, clone, and effect; matched Full B and Anchor B each use prepare, stage, transition, source-R0, source-R1, plus mode-specific proof, clone, and effect; own-revocation has a separate branch and R2 witness step ([run_v3_heldout_case.py lines 318–354](../../../tools/part5/run_v3_heldout_case.py#L318), [analyze_v3_heldout_costs.py lines 1033–1043](../../../tools/part5/analyze_v3_heldout_costs.py#L1033)). The acceptance fragment stores all step timings and those component summaries, but no case- or branch-wide elapsed field ([run_v3_heldout_case.py lines 2503–2532](../../../tools/part5/run_v3_heldout_case.py#L2503)).

The heldout cost analyzer validates those journal durations and computes `shared_B = B:prepare + B:stage + B:transition + B:source-R0 + B:source-R1`, then `full_B = shared_B + proof-full + Full clone + Full effect` and `anchor_B = shared_B + proof-anchor + Anchor clone + Anchor effect`. Optional plus-pair-view values add the separately timed `pair-view` credential-preparation step to each branch. Replay, disabled-config, and ambiguous-restart costs are reported as separate audit work and excluded from matched B totals ([analyze_v3_heldout_costs.py lines 239–272, 1033–1043](../../../tools/part5/analyze_v3_heldout_costs.py#L239), [1144–1165](../../../tools/part5/analyze_v3_heldout_costs.py#L1144)). Its `basis` and formulas explicitly describe these as component accounting ([same file, lines 1148–1153](../../../tools/part5/analyze_v3_heldout_costs.py#L1148)).

So heldout is directly timed at the step and bounded-child level, including successful application effects. The matched Full/Anchor branch totals are still arithmetic sums, not direct measurements across the complete path. The runner does not wrap a single timer around setup through effect for each branch. Transaction bytes, compute units, and fee lamports are read from pinned successful effect reports and kept separate from wall-time accounting ([analyze_v3_heldout_costs.py lines 1162–1165](../../../tools/part5/analyze_v3_heldout_costs.py#L1162)).

## Smallest later instrumentation to close the gap

No report-only change can convert the existing component sums into direct whole-session timing. A later, separately registered measurement harness would need to add a paired arm-level clock and retain the current component timings for attribution:

1. Freeze the measurement boundary, workload, root-count pattern, and setup-sharing rule before running. Use identical credentials, circuit/setup/VK, exact action, hardware, root schedule, and application effect. Use separate byte-identical pre-execution ledger clones so the same request is not consumed twice.
2. For each Full and Anchor arm, start one monotonic timer before the earliest charged per-credential/per-action operation. Include any shared prepare/stage/transition work that the declared workload charges to that arm, the mode-specific clone and proof/refresh path, verification, application submission, finalized effect, and cleanup. Stop only after the owned processes are gone and the arm's evidence is durable. Keep the outer timer owner and timestamps in a pinned per-arm receipt.
3. Decide how circuit-wide setup/material is shared. If the claim includes that setup, place the real setup operation inside the directly timed workload. If it is a shared one-time cost, time and report it separately with an explicit, evidence-backed sharing basis; do not silently amortize it or call the post-setup arm timer an all-in first-use total.
4. Derive each paired delta and savings fraction from the two direct arm durations, then report individual pairs, spread, median, sampled break-even, and the registered 20% decision. Do not substitute a sum of the old independently timed components for the direct arm value. Preserve component clocks to explain any direct-vs-component difference.
5. Include realistic failed/retried work in the selected scenario or report it separately as a clearly bounded outcome. Add serialization/reload and retained-byte measurements only if that lifecycle is in scope and implemented. Wall time can satisfy the plan's wall-time path; do not claim complete-tree CPU until its accounting boundary is separately qualified.
6. Apply the same frozen timing boundary and analysis unchanged to heldout cases. A training-only direct measurement would not establish heldout behavior; the plan requires a separate frozen heldout performance run and clear workload/source distinctions ([plan lines 104–107](../../superpowers/plans/2026-10-16-v3-x509-application-benefit.md#L104)).
