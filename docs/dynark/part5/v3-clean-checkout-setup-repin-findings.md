# Fresh v3 setup: clean-checkout repinning findings

**Snapshot: 2026-10-18.** This is a source audit; no build, setup, proof, or validator was run. It describes a new package identity, not a way to reproduce Training-010's historical receipts.

## What currently blocks a fresh package

The fixed circuit identity is reproducible from source, but the setup and proof CLIs authorize one historical witness/setup/package chain:

- `circuits/credential-v3-bounded/qualification/prover/src/main.rs:39-44,390-453` pins the current R1CS, WASM, profile, circuit schema, and witness-suite report. The suite report includes measured times (`tools/part5/witness_suite.cjs:62-96`), so a fresh successful run gets different bytes and a different SHA even when it checks the same 52 cases. `accepted_suite` rejects a different report SHA before setup (`circuits/credential-v3-bounded/qualification/prover/src/main.rs:450-453`). The report can be generated before changing the setup source; it does not include setup source or binary identity, so this is not circular.
- The setup CLI records its source, lockfile, executable, suite path/hash, generated PK/VK hashes, and elapsed time in `setup-manifest.json` (`circuits/credential-v3-bounded/qualification/prover/src/main.rs:458-468,508-563`). The package-check report also includes measured elapsed time (`circuits/credential-v3-bounded/qualification/prover/src/main.rs:711-718`). Thus a new run necessarily has different setup/check report bytes and a random package identity.
- `circuits/credential-v3-bounded/qualification/proof-runner-v1/src/artifacts.rs:468-507,510-531` and `circuits/credential-v3-bounded/qualification/proof-runner-v1/src/context.rs:510-523` pin the historical setup manifest (`d31f82…`), package-check report (`4a8d52…`), package digest (`61d941…`), setup binary/source/lock, and ordinary VK. These are intentional trust gates, not paths that can be satisfied by copying a new report under an old filename.
- The current `check-package` CLI accepts a private assignments manifest and checks all 18 exact accepted witnesses (`circuits/credential-v3-bounded/qualification/prover/src/main.rs:584-620,641-718`). The witness suite emits the WTNS/public files and its report (`tools/part5/witness_suite.cjs:74-96`). `tools/part5/create_v3_accepted_assignments_manifest.py` now constructs the required private manifest from a reviewed fresh suite SHA; this source-level bridge has not yet been exercised in a fresh setup run.
- Fresh campaign tools also need new pins: `tools/part5/prepare_proof_inputs_v1.py:21-27,124-171,177-184` fixes the old report/setup/package and `v3-compile-001` paths; `tools/part5/freeze_v3_campaign_cohort.py:28-30,183-216` fixes the old setup and compile directories. The proof-runner test at `circuits/credential-v3-bounded/qualification/proof-runner-v1/src/artifacts.rs:622-627` opens the ignored historical setup manifest, so its v2 counterpart must use a fixture-free/synthetic provenance test or an explicitly supplied fixture rather than fail on a clean clone.

## Smallest safe versioned path

Keep the accepted v1 sources, binaries, and Training-010 receipts unchanged. Add a v2 setup/proof source pair and versioned input-preparation/freeze tools (or parameterized equivalents with an independently reviewed, immutable pin record). A fresh run should proceed in this order:

1. In a clean checkout, install pinned dependencies and compile into a fresh `v3-compile-002`. Confirm the existing R1CS/WASM/profile/symbol pins before using the witness suite. The reproduction guide documents the Circom command and expected hashes (`docs/dynark/part5/v3-clean-checkout-reproduction.md:116-145`); it also records that Circom and several host tools are not repository-pinned (`docs/dynark/part5/v3-clean-checkout-reproduction.md:7-9,110-124`).
2. Generate a fresh private corpus and run the bounded 52-case witness suite into a new private directory. Use the 900-second / 4-GiB suite limit in `tools/part5/WITNESS-PROPOSAL.md:14-42`. Review its full report, then put that exact report SHA into the new setup-source version. Keep the unchanged R1CS, WASM, profile, and semantic-schema pins; reject any mismatch.
3. Run the assignments-manifest constructor after reviewing the fresh suite report. It selects exactly the 18 passed `expected=accept` cases and records the report path/SHA plus each matching WTNS/public path/SHA. Its source checks exact count/names, path containment, hashes, and stale or extra records, then uses create-exclusive mode-0600 output under the suite's mode-0700 directory. Independently review its output SHA before `check-package`.
4. Test and build the versioned setup launcher, then use its existing interfaces with fresh outputs: `setup R1CS WASM PROFILE SUITE SUITE_SHA FRESH_SETUP_DIR` (`circuits/credential-v3-bounded/qualification/prover/src/main.rs:508-514`) followed by `check-package R1CS WASM PROFILE SETUP_MANIFEST SETUP_SHA ASSIGNMENTS ASSIGNMENTS_SHA FRESH_CHECK_DIR` (`circuits/credential-v3-bounded/qualification/prover/src/main.rs:584-603`). Keep the generated PK, witnesses, assignments manifest, and raw private reports owner-only.
5. After those outputs exist, record their measured hashes and package identity in a reviewed v2 pin record. Pin the fresh setup/check hashes, package digest, setup binary/source/lock, VK, and witness-suite hash in a new proof runner. Update the v2 packet preparer and freeze tool to consume those exact pins and explicit fresh paths; do not make a report authorize itself. Add stale-hash rejection tests for every pin and replace the old-manifest filesystem test with a clean-checkout-safe provenance test. Run only source/unit tests before a separately bounded clean-checkout rehearsal.

This is a *versioned repin*, not simply changing one constant: the suite hash must be known before building v2 setup; the setup manifest/check report and random package digest are known only after their respective runs; the proof runner and packet/freeze tools must then bind that complete chain. Current v1 tests and helpers should remain available for validating the historical package.

## Large artifact boundary

At this checkout, the generated public compiler outputs measured 169,075,640 bytes (`credential.r1cs`), 227,653,284 bytes (`credential.sym`), and 9,994,325 bytes (`credential.wasm`). The checker caps R1CS at 192 MiB and the input-map path caps symbols at 256 MiB (`tools/part5/witness_check.py:61-70`; `tools/part5/prepare_proof_inputs_v1.py:141-145`). These files need not be committed: a clean run can rebuild them with a pinned Circom toolchain, or an evidence bundle can distribute them by exact SHA outside ordinary Git files.

The same snapshot's 18 WTNS outputs were 25,113,548 bytes each (about 452 MB total), and `development.pk` was 159,122,357 bytes. These are private run artifacts, not public bundle contents: the setup launcher enforces owner-only files/directories and caps the PK at 512 MiB (`circuits/credential-v3-bounded/qualification/prover/src/main.rs:70-89,157-184,199-207,575-581`); the witness proposal labels the assignments and inputs private (`tools/part5/WITNESS-PROPOSAL.md:27-42`). A clean reproduction must generate new private values locally. Publish only reviewed, path-scrubbed receipts and hashes; do not publish the PK, corpus inputs, WTNS, or raw private assignments manifest.
