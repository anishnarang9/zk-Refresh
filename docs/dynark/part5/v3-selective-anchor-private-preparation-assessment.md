# Selective updates and the v3 Anchor preparation cost

## Finding

The accepted selective engine is a plausible way to avoid eagerly materializing both full Anchor projection tables, but current evidence does not show that it can materially reduce the v3 campaign's private preparation. The frozen v3 proof runner calls `Anchor::create` for each credential and times that whole call as `private_anchor_prepare_ms` ([proof runner](../../../circuits/credential-v3-bounded/qualification/proof-runner-v1/src/main.rs:911)). `Anchor::create` captures the full witness and then computes both `uk.project` tables ([anchored.rs](../../../crates/dynark-bn254/src/anchored.rs:230)). Selective creation still calls `capture` and creates the full initial proof, but skips those two eager `project` calls ([selective.rs](../../../crates/dynark-bn254/src/selective.rs:233)). Thus it could save the projection portion; the existing reports do not split that portion from capture or quantify the potential saving.

The scale and update shape are serious compatibility gates. The v3 circuit uses a domain of 1,048,576 and 784,796 assignment fields ([artifacts.rs](../../../circuits/credential-v3-bounded/qualification/proof-runner-v1/src/artifacts.rs:22)); `SelectiveConfig::small()` only admits domain and assignment sizes up to 1,024, with 32 MiB private and 64 MiB total state ceilings ([delta.rs](../../../crates/dynark-bn254/src/delta.rs:17), [selective.rs](../../../crates/dynark-bn254/src/selective.rs:42)). The v3 package therefore needs a separately specified resource configuration before it can even be evaluated. Also, the accepted v3 near-witness update had 5,081 changed fields ([witness-suffix-oct14.md](../phase-2/evidence/witness-suffix-oct14.md:44)); the selective default allows only 1,024 anchor-relative assignment deltas. If the exact Training-011 pair has the same support, it will leave selective mode. Even below that cap, one update can request at most four A/B projection entries, with two cold misses; overflow falls back and latches `FullOnly` ([selective.rs](../../../crates/dynark-bn254/src/selective.rs:462), [selective.rs](../../../crates/dynark-bn254/src/selective.rs:524), [selective.rs](../../../crates/dynark-bn254/src/selective.rs:821)). The exact Training-011 transition's changed-field and row-demand counts have not been established here.

The accepted Phase-2 gate established exact correctness and bounded lifecycle behavior on small fixtures, not selective speed or credential-scale benefit ([T7 handoff](../phase-2/HANDOFF.md:48)). Its 19 passing tests and small fixture process measurements cannot be used to predict this workload. The separate incremental-witness pilot's 15.67–16.01× warm improvement is a different optimization; it materializes a complete WTNS and also benefits Full proving, so it is not evidence for SelectiveState or an Anchor-only saving ([witness-suffix-oct14.md](../phase-2/evidence/witness-suffix-oct14.md:84)).

The economic upside is limited to work inside `Anchor::create`: public `UpdatingMaterial::prepare` remains a separate, paid ~732.5-second stage. In the earlier v3 pilot, private preparation was 704.394 seconds while refresh plus verification was 0.922 seconds ([Anchor pilot](v3-anchor-pilot-gate.md:17)). Selective mode cannot remove the full `capture` cost or public setup; if the update exceeds its bounds, full fallback adds work and erases the expected benefit. No current timing supports a savings claim.

## Smallest falsifiable follow-up

After Training-011 completes, keep its frozen source and receipts unchanged. In a separately frozen experimental copy, use one exact Training-011 R0-to-near request pair and first measure its validated assignment delta, A/B row demand, cold misses, and required memory. Stop the experiment if it exceeds the configured bounds; do not raise a cap after seeing the result. If eligible, run one serial matched pair with the same package, setup, assignment, transition, and request: current `Anchor::create`/`update` versus `SelectiveState::create`/`begin_update`/`advance`. Verify each resulting proof ordinarily and time both initial preparation and the complete paid path, including fallback. Report the projection-saving component separately from capture and transition work. Treat a ≥20% reduction in total active-session work as the registered threshold for a material campaign benefit; a faster create call alone is insufficient.

This is a recommendation only. No source, build, proof, or validator work was performed for this assessment.
