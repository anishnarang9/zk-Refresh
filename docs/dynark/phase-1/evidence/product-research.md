## Recommendation and user decisions

**Proposal:** Start with one consenting organization issuing dedicated RSA end-entity authorization credentials to its eligible members. A native local Rust client proves eligibility and holder-key authorization to execute one permissioned instruction that appends an approved submission commitment to an application account on Solana. The commitment and destination are explicit action parameters; the receipt is ancillary to the actual state change. The organization controls admission and revocation; the holder controls the RSA signing operation and proving. This is a proposed pilot, not an existing customer, measured workload, or approved deployment.

Use a dedicated issuing key enrolled under one explicitly configured organization trust anchor. Prove the leaf certificate signature, signed authorization fields, holder signature, and active membership. Validate any parent CA path during issuer enrollment under an explicitly trusted operator boundary. Do not claim a proved chain. Preserve strict equality with the current authorized root at execution. The product can use full proving whenever private preparation does not repay within the action session; complete DYNARK support remains the engine objective.

| Decision for user | Recommended choice | Concrete alternative / trade-off |
|---|---|---|
| Initial client/device | Native local CLI/SDK on existing Apple M3 Pro class desktop; qualify Linux x86-64 before portability claims | Browser-first adds signer integration, worker/memory limits, and public artifact distribution work before evidence of feasibility; mobile adds device/key-provider and suspension/energy qualification |
| Issuer/path trust | One dedicated organization issuing CA; independently validated and authorized enrollment of its parent path | In-circuit bounded chain validation reduces reliance on enrollment correctness but adds signatures, constraints, path policy, setup versions and witness cost; arbitrary OS/browser trust stores admit authorities unrelated to the intended organization |
| Eligibility statement | Signed purpose + stable organization/group identifiers in an issuer-defined authorization extension, with digitalSignature KU and explicit purpose EKU | Reuse general clientAuth certificates with issuer enrollment/registry admission attesting membership: easier issuance integration but moves authorization semantics to a trusted enrollment operator; a subject O string alone does not establish application permission |
| Revocation safety | Authenticated issuer feed, committed freshness deadline, and fail-closed authorization/pause when source freshness expires | Continue accepting current root during feed failure: better availability but permits credentials whose issuer status is unknown; this materially changes trust and requires approval |
| Privacy | Initially retain public issuer key identifier and exact validity dates, explicitly document leakage | Keep dates private and prove a public validity interval/bucket: changes the circuit and retry dependencies; additional engineering and measurement are required |

The first three are the requested concrete requirement questions. Feed outage behavior, privacy, and exact protected effect should be ratified with them before circuit/product implementation. The engine work on the unchanged circuit can proceed independently.

## Supported credential proposal and signed-field eligibility

**Primary:** Certificate validity is inclusive and encoded as UTCTime through 2049 / GeneralizedTime thereafter. Certificate critical extensions, key usage, EKU, CA constraints and path policy require explicit processing within the relevant validation scope. See [RFC 5280 §§4.1.2.5,4.2,6](https://www.rfc-editor.org/rfc/rfc5280.html). This project should describe a restricted supported profile instead of claiming full PKIX conformance.

**Proposal:** The initial controlled profile is X.509 v3 DER, RSA-2048/65537 SPKI and issuer key, sha256WithRSAEncryption certificate signature, and RSASSA-PKCS1-v1_5/SHA-256 holder action signature. These choices continue the baseline suite, subject to consenting issuer feasibility. Signature length is exactly 256 bytes; signature integer is below the modulus; modulus is exactly 2048 bits and odd. SPKI, inner signature algorithm and outer signature algorithm must all match the permitted representations. Padding verification checks the complete expected encoded block, including SHA-256 DigestInfo. [RFC 8017 §§4,5.2.2,8.2.2,9.2,A.1.1](https://www.rfc-editor.org/rfc/rfc8017.html) defines those RSA representation/verification operations; [RFC 4055 §§1.2,5](https://www.rfc-editor.org/rfc/rfc4055.html) covers RSA algorithm identifiers in certificates. New keys should be generated by approved issuer/holder tooling; proving modulus size/oddness is not proving correct key generation.

Signed eligibility must establish: (1) precisely enrolled issuer key and issuer profile; (2) end-entity basicConstraints cA=false; (3) KU digitalSignature set, keyCertSign/cRLSign absent for the holder; (4) dedicated authorization-purpose EKU; (5) understood critical authorization extension carrying version, fixed-length opaque organization ID, fixed-length opaque authorization-group ID, and application-purpose identifier; (6) permitted signed validity interval; (7) holder RSA key from signed SPKI. Recommend singleton purpose EKU and authorization extension for the initial profile to avoid ambiguous permission unions. No real/private OID is invented here: issuer-assigned OID(s), exact DER bytes, organization/group IDs and issuance policy are unresolved configuration to be approved and allocated before implementation. A signed subject O can be retained for interoperability but should not be the authoritative eligibility predicate.

The proving circuit must extract these facts from the exact issuer-signed TBS bytes and compare them with profile constants or authenticated public policy. The host importer may reject unsupported input earlier, but its parsing result cannot be accepted as a free witness assertion. The authorized registry admission separately establishes the certificate is admitted and active; it does not replace the leaf signature or holder signature.

**Proposal, bounds pending corpus:** Plan bounded DER buckets, e.g. TBS ≤1024 or ≤2048 bytes, with exact encoded length and zero padding outside the signed length. These are engineering candidates, not observed real certificate sizes. Constrain tag/length minimality, integer sign/minimal encoding, BIT STRING unused-bit handling, field order, duplicate extensions, parent/child bounds, OID representations, complete input consumption and no ambiguous offsets. Support UTCTime plus bounded GeneralizedTime and reject unsupported dates explicitly. Restrict leaf extension set initially; unknown critical extensions fail, and unknown noncritical extensions are either safely skipped under a documented rule or explicitly unsupported. Do not accept arbitrary BER/indefinite lengths. The normative encoding reference is [ITU-T X.690 (02/2021), DER clauses 10-11](https://www.itu.int/rec/T-REC-X.690-202102-I/en); only its official publication landing page was retrieved here, so clause-level parser conformance remains a later review obligation.

**Primary:** Circom `<==` combines witness assignment and a constraint; `<--` alone does not constrain the assigned result. A runtime `assert` is a witness-program check and is not a substitute for a relation constraint. [Official Circom constraint-generation source](https://raw.githubusercontent.com/iden3/circom/master/mkdocs/docs/circom-language/constraint-generation.md), [official code-assertion source](https://raw.githubusercontent.com/iden3/circom/master/mkdocs/docs/circom-language/code-quality/code-assertion.md). Thus neither a host parser nor an accepted WASM witness establishes that all signed semantics are proved. Circuit/R1CS checks and adversarial witnesses are required when replacing the fixed template. No unconstrained-signal exploit is claimed from this inspection alone.

## Holder action and execution contract proposal

**Proposal:** Keep root out of the holder-signed action so unrelated revocations permit reuse of the same authorization signature. Root equality is checked independently at execution. Sign a labeled envelope containing the action digest; bind the digest to an exact canonical action encoding.

Candidate canonical layout (fixed byte sizes and explicit endianness; freeze with test vectors before implementation): domain label/version; 32-byte configured chain/deployment identifier; authorizing program ID; protected application program ID; registry account; circuit/profile/policy identifiers; operation discriminator; ordered effect account keys and their required roles; recipient; operation-parameter commitment; 32-byte random action ID; absolute action deadline. Length-prefix every variable byte string or use fixed lengths. Reject duplicate/extra accounts when the effect contract requires a unique ordered list. Program computes this encoding from execution inputs, checks its digest against the proof and validates the deadline. Bind parameters including the submission commitment and destination account to eliminate CPI/account/parameter substitution. The deployment identifier must be immutable/authenticated configuration known by both signer and program, not a caller-supplied claimed network name.

For compatibility with the current field representation, a candidate is `actionHash = OS2IP(SHA256(canonicalAction)) mod Fr`, and holder signs `"dynark-holder-action-v2" || BE32(actionHash)` with PKCS#1 v1.5/SHA-256. The circuit checks that exact envelope signature under the TBS-extracted holder key; the program recomputes the actionHash from exact effect inputs. The field reduction is part of the protocol; freeze canonical conversion and analyze its collision assumptions before adopting it. Alternatively retain the full digest as two 128-bit public limbs; that changes schema/verifier cost. Neither candidate is implemented or formally approved here.

A copied valid authorization can be relayed to carry out its same authorized effect; if only a designated submitter may execute it, add submitter identity to the signed encoding and require its transaction signature. Do not assume RSA holder identity equals transaction payer. Cancellation semantics need an explicit choice: local cancellation stops the client, while invalidating an already disclosed proof requires onchain cancellation/nonce state or expiry. Replay state is keyed by deployment/registry/action ID, updated only after all checks/effect success in the same transaction. Ambiguous transaction confirmation is resolved from receipt/effect state before another submission.

Candidate public schema can remain `[root, issuerKeyId, notBefore, notAfter, actionHash]` **only if** the eligibility policy is fixed by the authenticated circuit/verifier package and any execution policy fields are bound through actionHash. A selectable eligibility policy requires a proved public policy commitment or distinct fixed circuit/profile key; unsigned host policy values are insufficient. Each schema/circuit change creates a deliberate package/setup/verifier version and invalidates incompatible caches. A private credential identity, slot, certificate, signed claims, Merkle path and signatures remain witness data.

At execution require: current enabled circuit/profile and issuer configuration; latest root equality; publisher/source freshness deadline; inclusive leaf validity and enrolled issuer/path validity; action deadline; exact action binding; ordinary Groth16 proof acceptance; unused action; effect success. Historical-root grace remains excluded. Configuration changes, own revocation, holder renewal, issuer rotation or changed action invalidate the relevant cache; unrelated root changes alone can preserve signed action bytes.

## Controlled CA boundary, rotation and current RFC updates

**Proposal:** Enrollment authenticates an issuing CA key fingerprint, parent path/anchor, allowed organization/group/purpose, issuer validity bounds, revocation adapter, and policy/circuit versions. The enrollment operator validates CA signatures/basicConstraints/KU/path length/critical extensions and relevant name/policy constraints using a maintained validator. The issuer configuration records validation provenance; holders do not prove parent certificates in this pilot. Registry authority governance can suspend issuer configuration immediately on compromise rather than individually modifying every holder slot. Split authority for issuer enrollment, root publication, deployment and upgrade remains an operational decision.

Intermediate/root withdrawal invalidates all dependent enrolled issuing keys even when a holder leaf remains active. Enrollment must track ancestry, issuer validity and live status; one successful chain check at onboarding is not perpetual chain validity. A key rollover is a new fingerprint/profile configuration; permit a bounded approved overlap for old/new keys, then disable old key and invalidate caches. Holder renewal creates a new certificate digest and generation/admission; never reactivate a recycled slot for an old certificate. Existing program has one immutable issuer per registry and no enable/disable/rotation API (`program/src/lib.rs:178-216,487-502`), so these require deliberate integration changes.

**Primary:** Trust-anchor treatment is clarified by [RFC 6818 §§2,4,6](https://www.rfc-editor.org/rfc/rfc6818.html). Broad PKIX support additionally needs the complete validated path/policy behavior, not simply a chain of valid signatures. Policy validation was updated to an equivalent more efficient graph algorithm by [RFC 9618 §§1.1,4-5](https://www.rfc-editor.org/rfc/rfc9618.html); bounded input and policy processing are part of enrollment security.

The [RFC Editor RFC 5280 status page](https://www.rfc-editor.org/info/rfc5280/) listed **nine** updating RFCs when retrieved on 2026-10-10. Current applicability inventory:

## Signed issuer status to onchain effectiveness

**Primary:** OCSP acceptance checks include matching certificate ID, response signature/authorized responder and status time bounds; `good` does not independently prove issuance or certificate validity. [RFC 6960 §§2.2,3.2,4.2.2.2](https://www.rfc-editor.org/rfc/rfc6960.html). CRL profile/validation is in [RFC 5280 §§5,6.3](https://www.rfc-editor.org/rfc/rfc5280.html), with the mandatory CRL-signer KU presence check in [RFC 10007 §4](https://www.rfc-editor.org/rfc/rfc10007.html).

**Proposal:** Use directly issued complete signed CRLs for the first controlled issuer where possible: one scope, no indirect/delta CRL complexity. Authenticate signer/path and distribution-point scope, check thisUpdate/nextUpdate and monotonically tracked source versions, bind entries using issuer-key identity plus full certificate serial, and maintain admitted-certificate mapping. Explicitly reject unsupported indirect/delta/scoped CRLs rather than interpreting them as complete. If OCSP is necessary, validate CertID issuer hashes/serial, response algorithm/signature, authorized responder including delegated OCSPSigning usage, freshness, and responder lifecycle. Unknown/error/stale status is not good. OCSP is queried by the publisher rather than independently by every holder to reduce holder request leakage; it still leaks queried credentials to responder/publisher. Absence from a CRL only supports nonrevocation within authenticated complete scope and freshness.

Pipeline: issuer decides revocation → signed source makes it available → publisher detects and validates it → local authenticated registry transition disables leaf/issuer → transaction publishes new root/configuration → chain includes/confirms → holders fetch authenticated update → action executes against current chain state. Measure each timestamp separately. Effective onchain delay is source issuance delay + detection/poll delay + validation/queue delay + transaction inclusion delay (confirmation choice affects what the client treats as stable). Root-current semantics close the race after publication; they cannot eliminate preceding issuer/publisher delay.

Commit source identity/version/hash and an authorized `status_valid_until` to each publication/configuration. Chain clock must reject authorization after that deadline unless a fresh authenticated status attestation is published. Repeatedly publishing the same root without fresh issuer source must not renew the freshness window. Heartbeats that change only freshness metadata need not alter the Merkle root; this avoids manufacturing root churn while keeping feed health explicit. If snapshots do alter root, count them in observed churn. A program-enforced deadline constrains outage duration, but a trusted publisher can still misrepresent source validation: direct issuer signature verification onchain/in proof or separate independent attestors is a different trust architecture requiring approval.

Publisher obligations: correct admission/tree construction and authenticated feed consumption; prompt monotone publication; issuer/intermediate suspension; no reinstatement without approved status transition; retained audit/recovery evidence; authenticated snapshots/deltas; gap recovery; availability within freshness budget. Threats: signer compromise, malicious omission, replayed status, stale RPC, competing updates/version conflicts and outage. Protect signer, monitor lag, separate governance roles and define emergency pause/recovery. Availability budget and confirmation/finality policy are unresolved; do not invent an operational SLA from prototype timings.

## Privacy, clients and workload evidence

**Code + inference:** Five public signals expose issuerHash and exact notBefore/notAfter (`credential.circom:117`), which can partition/identify small issuance cohorts. Action ID, recipient, registry and program are clear instruction data (`program/src/lib.rs:76-81,97-107`); receipts retain action/root/time. Transactions reveal timing, payer/fee source, root version and retry behavior. ZK hides certificate/slot/signatures in the statement, not these metadata or local cache contents. A certificate visible elsewhere may be correlated using exact dates and issuer even without its onchain digest.

**Proposal:** Document RPC/submission linkage, path-query slot leakage, publisher admission mapping, CRL serial visibility and feed timing. Public snapshot/delta broadcast avoids per-holder path queries but may reveal leaf changes and known certificate/slot mappings; public certificate digest commitments are susceptible to matching known public certificates, not hiding them by hashing. Compare full-download/public-broadcast and per-slot retrieval before promising anonymity. Keep credential/slot, dependency footprints, signer handles, witnesses and private-cache identifiers out of telemetry. Local state needs authenticated versioned storage and OS-protected encryption where persisted; do not promise perfect secure deletion. Proving outsourced to a service discloses private witness/preparation inputs unless a separately evaluated protocol changes that boundary.

**Historical:** Existing `results/dynark/feasibility.md:15,25-50` reports M3 Pro/18 GiB, four Rayon threads, five ordered measured proof pairs; 551.61 s private preparation; 64 MiB serialized cache; 1.50 GiB lifetime RSS / 2.66 GiB footprint; derived approximately 305 comparable refreshes for private preparation payback with shared public key. These are existing synthetic measurements/derived estimates, not fresh trials, device requirements, or evidence users experience that many retries. New-action witness footprint is 104,175 values; same-action root refresh changes less. Credential validity lifetime does not imply action cache reuse lifetime.

**Proposal:** Native signer interface accepts a certificate/key handle and returns the requested exact scheme signature with consent/progress/cancellation; validate returned signature against certificate SPKI locally. Start with approved OS/software signer and qualify PKCS#11/hardware adapters on actual issuer devices. Existing fixtures embedding PEMs are not the product signer interface. Some holders/providers may not permit arbitrary application signing or this algorithm; that is an eligibility/device blocker to establish with the consenting organization. No OS/hardware RSA support claim was tested here.

**Primary + inference:** WebCrypto specifies RSA signing/import but leaves key-store implementation abstract and module discovery/provisioning outside scope. This is not a portable guarantee that a site can access an already installed enterprise certificate key. [W3C Web Cryptography Level 2 §§4.2-4.3,5.2,20](https://www.w3.org/TR/webcrypto/). Browser proving/worker execution remains plausible but unmeasured; private-key import or native bridge would require separate review. Mobile requires actual signer/device capability, peak memory, battery/thermal/suspension, artifact download/storage and recovery measurements before support claims.

**Hypothesis:** Unrelated revocations during a pending action cause enough expensive retries for cheaper preparation/incremental witness work to help. No consenting organization update trace, submission workload or retry distribution is available. Authorization count is not root-update count. Measure issuance, holder/issuer revocation, renewal, batches and actual snapshot-induced root changes separately; keep freshness-only updates distinct. Test sessions with 0/1/2/5/10/100 refreshes, cancellations, eviction/reload, offline catch-up and distinct new actions. Synthetic Poisson/burst/adversarial churn sweeps are stress scenarios, not production evidence. Select full/anchored/fully dynamic mode from total lifetime cost and positive payback; expose bounded failure under churn, not historical-root fallback.
