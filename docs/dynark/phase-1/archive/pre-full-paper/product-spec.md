# Private credential authorization: product specification

October 10, 2026. **X.509/RSA, DYNARK/BN254, strict execution-current-root, native desktop first, administrator-enrolled controlled organization CA, dedicated signed authorization fields, pause-on-stale issuer status, and a permissioned work-request queue are accepted.** The user confirmed D06–D10 in this chat. Exact issuer profile/encoding, freshness timeout, device budget and request schema still require qualification. This document prepares later phases; it does not authorize deployment or a private credential corpus. Detailed source and standards analysis belongs in [product research evidence](evidence/product-research.md).

## First use case and statement

The selected use case is a controlled organization whose eligible members receive RSA credentials and may authorize a permissioned work request recorded by a Solana application. The pilot effect appends one authorized request to a program-owned queue and consumes its action nonce atomically. It must bind the exact request type, payload commitment, recipient and relevant accounts; a proof receipt alone is not the protected effect. The user selected this pilot action; no customer demand or partner has yet been established.

Eligibility means: an enrolled issuing key signed the exact supported certificate bytes; its signed opaque organization/group identifiers and dedicated authorization purpose satisfy the versioned application policy; its holder public key verifies a fresh action authorization; its credential leaf is active under the execution-current registry root; its signed validity interval includes execution time; issuer enrollment and policy/circuit version remain enabled and valid; authenticated issuer status meets the execution-time freshness policy; and the action has not already succeeded. Possession of a public website certificate without legitimate holder signing capability does not meet this statement. An organization name string alone does not establish current membership; issuance policy and active-registry management remain trusted responsibilities. Use dedicated signed authorization fields under D10; issuer-defined extension and purpose EKU are the proposed concrete encoding. Their OIDs and bytes require issuer agreement, and none is invented or approved here. Reusing a general clientAuth certificate would require a different membership-attestation trust choice and is outside accepted D10.

The holder signs a canonical, domain-separated action authorization through a local signer. Proposed v2 message binds network identity, program, registry, policy/circuit version, action nonce, recipient, exact effect/account digest and any action deadline. The circuit verifies the signature using the key extracted from signed certificate bytes. The program reconstructs the expected digest from the instruction and accounts. A client-provided digest is never the sole authority for what executes. Domain bytes and encoding require one versioned specification shared by host, circuit and program, with ambiguity/cross-network tests.

Current v1 public signals are `[root, issuerHash, notBefore, notAfter, actionHash]`; the circuit's instance includes constant one before these. Preserve this schema for Phase 2 engine work. Proposed profile/domain changes belong to a separately versioned relation in Phase 3 and integration in Phase 4. The baseline host/program action digest binds program, registry, fixed policy version 1, recipient and action ID but lacks explicit network identity and a general effect-argument digest (`program/src/lib.rs::action_digest`). Do not silently change its original keys or claim v2 support.

## Profile proposal and honest existing scope

| Area | Current inspected baseline | Proposed first supported profile / qualification |
|---|---|---|
| Signed bytes | Exact synthetic 439-byte TBS; static bytes constrain issuer/subject organization, encodings and algorithm identifiers | Canonical bounded DER; all tag/length/offset/algorithm/key/extension claims proved from signed bytes. Declare supported size buckets after corpus inventory; 439 is not a real-world maximum |
| RSA | Issuer and holder RSA-2048/e65537; two SHA-256 PKCS#1 v1.5 verifications | Retain this suite if the chosen issuer and signer support it; reject RSA-PSS, other exponents/sizes or schemes until separately versioned and tested |
| Subject/eligibility | Fixed template organization and subject; no extension-bearing accepted template | Explicit signed opaque organization/group/purpose fields, dedicated issuing-CA policy, end-entity basicConstraints, digitalSignature key usage and dedicated purpose EKU. Reject ambiguous/duplicate extensions and unsupported critical extensions |
| Dates | Signed UTCTime fields, years 2000–2049, public exact dates; execution-time check external to SNARK | Both supported UTCTime and GeneralizedTime, calendar/boundary validation, execution clock authoritative. Interval inclusive at endpoints as current program; specify deadline separately |
| Chain | Issuer key binding and synthetic configured issuer; no enrollment workflow or arbitrary proved chain | One explicitly enrolled issuing CA key; validate chain and authority at enrollment under declared trusted administrative process. Never describe this as in-circuit full PKIX validation |
| Registry | Depth 10, 1,024 leaves; TBS digest, slot and active bit bound | Keep depth 10 for engine baseline. Later depth/version migration with immutable leaf identity and safe slot reuse; revoke old credential before replacement and prevent resurrection |
| Signer | Synthetic local private-key fixture | Local OS/token adapter where compatible; never require exporting a real private key merely for benchmarking. RSA signing of the exact application message must be explicitly supported by the device/key policy |

RSA signature verification must validate the full EMSA encoding and length/range checks, not merely a modular exponentiation or digest substring. These obligations follow [RFC 8017 §§8.2 and 9.2](https://www.rfc-editor.org/rfc/rfc8017); the planned corpus includes malformed padding/DigestInfo, wrong modulus, exponent, hash and signature length.

PKIX profile and path/CRL semantics must be mapped to the actual trust boundary using [RFC 5280 §§4–6 and its update list](https://www.rfc-editor.org/info/rfc5280/). The linked evidence records which updates apply to enrollment, naming, policy processing and revocation. Do not claim every RFC feature is supported. A host parser may reject unsupported inputs but cannot supply unconstrained signed-field facts to the proof. Circom witness-only assignment (`<--`) does not create a constraint; assignment with constraint (`<==`) does. See [official Circom constraint semantics](https://raw.githubusercontent.com/iden3/circom/master/mkdocs/docs/circom-language/constraint-generation.md).

No consented real credential corpus exists in this phase. Pilot qualification must inventory DER/TBS sizes, RSA suite, dates, extensions, chain depth, key access and certificate/key policy with explicit permission. Synthetic public equivalents should cover the same shape. Missing corpus blocks final profile limits and device qualification, not the unchanged-circuit engine.

## Trust, revocation and availability

The issuing authority determines eligibility and signs credentials. The enrollment administrator decides which issuing keys/policies are accepted and validates any upstream chain. Enrollment tracks issuer validity, ancestry and ongoing status; a successful chain check at enrollment does not authorize an expired or subsequently withdrawn issuer indefinitely. The root publisher is trusted to translate authorized enrollment/revocation events faithfully and promptly. Solana authenticates publisher authority and root version transitions, not the truth of an omitted revocation event. Separate these authorities operationally; publisher compromise/omission is a documented threat.

Credential revocation identifies `(issuing key/version, certificate serial or canonical certificate digest)`, resolves the correct leaf, authenticates source authorization, deactivates membership and publishes a monotonic root version. Renewal uses a new identity and cannot reactivate an old credential through slot reuse. Issuer/intermediate compromise disables affected issuer enrollment immediately via a separately authenticated policy update, with a rebuild/migration plan for its descendants. Key rotation creates a new issuer version and invalidates affected private caches; overlapping acceptance is explicit policy, not implicit key substitution.

A CRL/OCSP adapter must authenticate signer authority, scope, certificate identity, update/freshness intervals and applicable algorithms; maintain monotonic source state; reject replay/out-of-scope or unknown results; and record source-observed, publisher-accepted and onchain-effective timestamps. Standards context: [RFC 6960](https://www.rfc-editor.org/rfc/rfc6960) and RFC 5280 CRL validation; exact adapter scope is later work. OCSP `good` alone is not an eligibility assertion.

Accepted D09 fail-closed operation binds authenticated status freshness to policy, with a no-change heartbeat permitted when the authority has freshly checked its source. A repeated root timestamp alone must not refresh stale issuer evidence. Timeout and outage recovery require a pilot service agreement; no numeric value is approved. This is distinct from accepting a historical root: **every accepted proof still uses the latest execution root**. Current strict policy accepts a current root of any age, so neither feed freshness nor pre-publication revocation delay has been solved by the prototype. Delay is measured from source revocation through publication and chain execution; do not call it instantaneous global revocation.

## Architecture and state interfaces

| Boundary | Contract and rejection behavior |
|---|---|
| Circuit/public package | Immutable R1CS, witness executable, profile/public-schema hash, reduction/domain/curve, PK/VK/setup identity and UK format. Validate package signatures/hashes and exact compatibility before use |
| Private credential state | Certificate data and signer handle; dependencies explicitly identify profile/issuer/credential generation. Do not embed raw signing keys in proof caches |
| Action state | Canonical action, signature, exact public statement, witness generation, immutable anchor or fully dynamic state, and retry deadline. Treat action change as invalidation unless a proved transition is implemented |
| Engine input | Validated complete witness or normalized sparse transition with base/target generation identities. Reject constant-one mutation, wrong index spaces, noncanonical fields, key/domain/schema mismatch and inconsistent expected public values |
| Engine output | Complete ordinary proof plus public statement and committed cache-generation metadata. The caller never receives a proof paired with a half-updated cache |
| Registry/witness client | Authenticate snapshot/deltas against chain-confirmed root; bounded sequence catch-up, gap detection, rollback handling and full-snapshot recovery. Untrusted transport cannot supply accepted false membership |
| Submission | Recheck current state, submit exact action, classify stale-root/revoked/expired/unknown-confirmation distinctly. Bound retries; coalesce to newest authenticated root; check receipt before replaying uncertain execution |
| Program/application | Validate account ownership/identity, authority, enabled issuer/version, execution clock/root, expected action digest and unused nonce; ordinary verification; protected effect and nonce consumption atomically |

Local cache identity contains circuit/setup/reduction, private credential/action identity, issuer/policy version, witness/root generation, domain and serialization version. It is not a public credential identifier. Persistence uses authenticated envelopes, OS-protected encryption keys, restricted permissions, rollback/version checks and explicit invalidation. Crash recovery either restores a complete committed generation or rebuilds; fail closed on corrupted/mixed state. Do not promise perfect erasure on general storage.

## Privacy and platform limits

The current public issuer and exact certificate dates can narrow an anonymity set. Recipient/action, RPC timing, repeated retry statements, fees/payer accounts and witnesses requested by slot create further linkage. Zero knowledge of private circuit inputs does not hide those observables. Log only aggregate workload counters by default; exclude certificate bytes, stable holder identifiers, private cache contents, proof randomness and detailed witness fingerprints.

A witness service learning a queried slot can correlate a user with a leaf. Broadcast deltas/local catch-up avoid per-slot requests but increase bandwidth and can still expose issuance associations in feed data. Stronger private retrieval requires separate design and evaluation. Outsourced witness preparation exposes private data unless a separate privacy protocol is established; it is not a free performance optimization.

Native desktop is the accepted initial target under D06. Browser memory limits, WASM threading/isolation, storage, cancellation and signer access need independent tests; mobile also requires thermal/energy/background-lifecycle and key-adapter qualification. One occupied M3 Pro measurement cannot qualify any of those environments.

## Workload and acceptance gates

There is no measured pilot update-rate or retry distribution. Evaluate 0/1/2/5/10/100+ refreshes per action, varying near/far/batched updates, new actions, abandonment, eviction, cold reload and offline catch-up. Illustrative churn sweeps (one root/day, one/hour, one/minute, one/second plus bursts) are stress hypotheses, not observed organizations. Registry population, authorization rate and actual root-update rate are separate variables. Do not delay revocation publication to produce a favorable workload.

Product acceptance requires: supported signed credentials and legitimate holders execute exactly the bound action; malformed/unsupported/wrong-organization/wrong-usage/expired/untrusted/revoked credentials fail precisely; same-action unrelated revocation can refresh under strict policy; issuer disable/rotation, missed updates, corrupted cache, replay, substituted accounts and uncertain confirmation recover safely; preparation plus retries plus background work yields positive measured session savings for the selected workload; and the selected device stays within a ratified resource budget. Roadmap subsecond/3×/16-MiB/512-MiB goals remain unachieved provisional targets.
